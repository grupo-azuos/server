# Infra v1.0.1 — DigitalOcean + Cloudflare

Primeira etapa da migração: **2 VPS + 1 cluster Postgres gerenciado com redundância**, tudo na DigitalOcean,
com o DNS na Cloudflare. Vem da [v1.0.0](v1.0.0.md).

## Contas

- Um e-mail de TI (ex.: `ti@grupoazuos.com.br`) é dono de todas as contas: DigitalOcean, Cloudflare, AWS,
  Resend e Registro.br.
- MFA obrigatório, acesso nominal e cofre de senhas.
- Uma conta-membro da AWS por empresa (AWS Organizations), com faturamento consolidado.

|---|---|---|

### Migração dos domínios

**`grupoazuos.com.br`** (Registro.br, titular no painel do Registro.br): no domínio, conferir
**Servidores DNS** = os da Cloudflare e trocar **Provedor de serviços** de HSTDOMAINS (Hostinger) para
**nenhum**, para o domínio não ficar preso à Hostinger.

**`grupoazuos.com`** (Hostinger → Cloudflare Registrar). O Registrar só aceita domínio já ativo na Cloudflare
e com mais de 60 dias desde o registro ou a última transferência.

1. Cloudflare: **Add a domain** → `grupoazuos.com`, plano Free. Conferir os registros importados e anotar os 2
   nameservers.
2. Hostinger (Domínios → `grupoazuos.com`): desligar o **DNSSEC** e trocar os nameservers pelos da Cloudflare.
3. Esperar o domínio ficar **Active** na Cloudflare (minutos a horas).
4. Hostinger: desligar o **Domain Lock / Transfer Lock** e copiar o **código EPP**.
5. Cloudflare: **Domain Registration → Transfer Domains** → `grupoazuos.com`, colar o EPP e pagar
   (~US$ 10, soma 1 ano à validade).
6. Aprovar o e-mail de transferência da Hostinger (sem aprovar, conclui sozinho em até 5 dias).
7. Depois: redirecionamento de `grupoazuos.com` para o `.com.br` (Redirect Rule na Cloudflare).

## Virada do ops (NetBird e RustDesk saem do legado)

Prevista para 31/10 ou 01/11/2026. A virada é só do NetBird server e do RustDesk; o ops entra no
NetBird novo depois que o DNS virar.

| Etapa no ops | Situação (29/10/2026) |
|---|---|
| `docker`, `caddy` | no ar |
| `netbird` (server + dashboard) | no ar, vazio; recebe os dados do legado na virada. Sem certificado até o DNS virar |
| `cockpit`, `node-exporter-cadvisor`, `prometheus-grafana`, `komodo-core` | no ar, no IP privado da VPC (`10.132.0.2`); acesso por túnel SSH |
| `netbird-client` | por último, quando o domínio virar; depois rodar de novo as etapas acima (passam para o IP do NetBird) |
| `komodo-periphery` | depois da onboarding key criada no painel do Komodo |
| RustDesk | na virada |

**Antes (sem afetar ninguém)**

1. TTL de `netbird`, `komodo` e do RustDesk na Cloudflare em 1–5 min.
2. Firewall da DigitalOcean (tag `ops`): `3478/udp`, `21115-21117/tcp` e `21116/udp`.
3. Ensaio: cópia do `/opt/netbird` (`config.yaml` e `data/`) do legado para o ops, com o legado no ar.
4. RustDesk no ops com a pasta de dados do legado (a chave `id_ed25519` identifica o servidor para os clientes).

**Na virada (~10 min fora)**

1. Parar o NetBird do legado e copiar `/opt/netbird` de novo (pega o que mudou desde o ensaio).
2. Apontar `netbird`, `komodo` e o RustDesk para o IP do ops.
3. `docker restart caddy` no ops, para emitir os certificados na hora.
4. Etapas no ops: `netbird-client` e de novo `cockpit`, `node-exporter-cadvisor`, `prometheus-grafana` e
   `komodo-core` (saem do IP privado para o do NetBird).
5. Conferir: peers em **Peers** no painel, `netbird status` com `Connected`, cliente do RustDesk conectando.

Se der errado: DNS de volta para o legado e subir o NetBird de lá (os dados dele não mudam na virada).

## Banco

- **Cluster único** com primário e standby: o standby é uma réplica em tempo real que assume sozinha se o
  primário cair, no mesmo endereço de conexão. Cada nó custa US$ 60,90.
- **Um database e um usuário por sistema**, cada um com o seu pool do PgBouncer (connection pools do painel).
- **Acesso só pela VPC.** Nada de IP público liberado nas *trusted sources*.
- **Backup diário e restore por ponto no tempo** já vêm no gerenciado.

> cluster e, a partir de 30/11/2026, para todas. Standby passa a exigir a edição Advanced, com outro preço.

## Auth: login único com Better Auth

O `user-manager` troca o Supabase Auth (GoTrue) pelo **Better Auth**, como biblioteca dentro do próprio
serviço, com o database `user_manager` no cluster. O desenho do auth-forward não muda:

```text
navegador ─▶ Caddy ─▶ forward_auth ─▶ user-manager /verify
                         ├─ 200 + x-forwarded-user-{id,email,name,role} ─▶ app
                         └─ 401 ─▶ redirect para o login
```

- **Cookie no domínio raiz** (`crossSubDomainCookies` com `grupoazuos.com.br`): um login vale em todos os
  subdomínios.
- **`/verify`** chama `auth.api.getSession({ headers })` e devolve a identidade nos quatro cabeçalhos que os
  apps já leem.
- **Sessão em cache** (`cookieCache` e/ou `secondaryStorage` no Valkey): o forward_auth roda em toda
  requisição e não pode ir ao Postgres em cada uma.
- **O Caddy apaga os `x-forwarded-user-*` que vierem do cliente** antes do forward_auth. Sem isso, qualquer um
  forja a identidade.
- **Apps só respondem pelo Caddy.** Nenhuma porta de app exposta fora da VPC, senão o cabeçalho é forjável.
- **Plugins:** `admin` (papéis, bloqueio de conta) e `twoFactor` (obrigatório para TI). `organization` se o
  isolamento das três empresas for por tenant no login.
- **E-mails pelo Resend, nos mesmos fluxos do Supabase.** Cada fluxo do Better Auth tem um callback que envia
  pelo Resend, com templates no código (React Email):

  | Supabase | Better Auth | Callback |
  |---|---|---|
  | Confirmar cadastro | `emailVerification` | `sendVerificationEmail` |
  | Recuperar senha | `emailAndPassword` | `sendResetPassword` |
  | Trocar e-mail | `user.changeEmail` | `sendChangeEmailVerification` |
  | Convidar usuário | plugin `admin` (`createUser`) + link de definir senha | `sendResetPassword` |
  | Magic link | plugin `magicLink` | `sendMagicLink` |
  | Código por e-mail | plugin `emailOTP` | `sendVerificationOTP` |

- **No front**, as chamadas do `supabase.auth` viram as do `authClient` (ex.: `signInWithPassword` →
  `signIn.email`). Muda a chamada, não o fluxo.
- **Migração dos usuários:** ver [Migração do Supabase](#migração-do-supabase).

## Deploy sem downtime: blue-green

Padrão inicial, pode mudar. Cada app tem duas cópias na mesma VPS, `blue` e `green`, atrás do Caddy:

1. A cópia parada recebe a versão nova e sobe.
2. O health check dela tem que passar.
3. O Caddy vira o tráfego para ela.
4. A cópia antiga fica parada para rollback imediato e recebe a próxima versão.

Regras que o padrão exige:

- **Migração de banco compatível com as duas versões** (expandir e depois contrair): durante a virada, a versão
  antiga e a nova usam o mesmo database. Remover ou renomear coluna só no deploy seguinte.
- **Nenhum estado dentro do container:** sessão no Better Auth (Postgres/Valkey), arquivos no S3, cache no Valkey.
- **O `user-manager` também é blue-green**, porque se ele cair, cai o login de todos os sistemas.

## Migração do Supabase

Os 3 projetos (sistemas refeitos, Trilha e CRM) saem pelo mesmo roteiro, um projeto por vez. Base: o
[guia oficial do Better Auth](https://www.better-auth.com/docs/guides/supabase-migration-guide).

### Usuários: três bases viram um login só

| Supabase | Better Auth |
|---|---|
| `auth.users` | `user` (o UUID é copiado como está) |
| `auth.identities` | `account` (e-mail e senha viram `providerId: credential`, com o hash) |
| `is_super_admin`, `banned_until` | `role`, `banned` (plugin `admin`) |
| `raw_user_meta_data`, `raw_app_meta_data` | `additionalFields` (`userMetadata`, `appMetadata`) |
| Sessões | **Não migram:** todo mundo faz login de novo uma vez |

- **Senha:** o Supabase grava em bcrypt. O `user-manager` configura `password.hash` e `password.verify` com
  bcrypt, então os hashes entram como estão e ninguém troca a senha.
- **Script do guia** (paginado por cursor, em lote, com retomada por `resumeFromId`), rodado uma vez por projeto,
  na ordem (1) → (2) → (3).
- **Mesma pessoa em mais de um projeto:** o e-mail é a chave. Se o e-mail já existe no `user-manager`, o usuário
  não é recriado e o UUID antigo vai para uma tabela de mapeamento (`projeto, id_antigo → id`), usada na migração
  dos dados daquele sistema.
- **Plugins antes do script:** plugin que faltar (ex.: `phoneNumber`) faz o script pular o dado sem erro.

### Dados de cada sistema

1. `pg_dump` só dos schemas do app (sem `auth`, `storage`, `realtime`, `supabase_*`).
2. `pg_restore` no database do sistema no cluster.
3. FKs para `auth.users` viram coluna `user_id uuid` simples, e o mapeamento de IDs é aplicado.
4. RLS com `auth.uid()` não vem junto: a autorização passa a ser no código, com a identidade do forward_auth.

### Arquivos

Storage do Supabase → S3, com `rclone` pelo endpoint S3 do próprio Supabase. Os caminhos gravados no banco são
reescritos para as chaves novas.

### Corte de cada projeto

1. Ensaio completo em homologação, com cópia do banco de produção.
2. Janela de corte: nova rodada do script de usuários (pega quem se cadastrou ou trocou a senha desde o ensaio),
   dump final dos dados e sincronização final dos arquivos.
3. DNS do sistema para a VPS nova.
4. Projeto do Supabase em leitura por 1 a 2 semanas, com backup final, e depois desligado.

Os usuários de Trilha e CRM entram no `user-manager` **no corte de cada um**, não antes. Importar cedo deixaria
as senhas divergentes de quem trocar a senha no Supabase enquanto isso.
